# CLAUDE.md: Standing Rules for Every Session

This repo builds **Hearthfield Idle** (working title), a cozy idle farming, fishing and cooking browser game, one phase per session. The phase prompts are in `prompts/`; the runbook is `prompts/README.md`.

## Before you write code
1. Read `docs/GDD.md`, `docs/PROGRESS.md`, and the sections of `docs/BALANCE.md` and `docs/DATA_SCHEMAS.md` your phase touches. `docs/ART_STYLE.md` before any sprite or UI work.
2. Read the "Next-phase notes" of the latest entry in `docs/PROGRESS.md`. Reuse existing patterns (actions, panels, sprites, tests); do not invent parallel ones.
3. If the docs and the code disagree, the code is what ships: fix the doc or the code in the same PR and note it under *Deviations*.

## Architecture rules
- **Game logic lives in `src/systems/`** as deterministic functions of `(state, ctx, dt)` where `ctx = { data, rng, mods, events, calendar }` (see `docs/DATA_SCHEMAS.md` §7). A system may mutate only the `state` passed to it. **No DOM, canvas, audio, `localStorage`, `Date.now()`, `Math.random()` or event-bus imports in systems.** Systems push `GameEvent`s to `ctx.events`; the loop flushes them to the bus.
- **Content lives only in `src/data/`**, typed with the id unions in `src/data/ids.ts`. No gameplay numbers hard-coded in systems, UI or rendering; constants that are formula parameters live in `src/data/balance.ts`.
- **Rendering lives in `src/render/`, UI in `src/ui/`.** Both read state and send actions through `dispatch()`. They never mutate state directly.
- **All randomness goes through the seeded RNG in `src/core/rng.ts`**, whose state is stored in `GameState.rngState`. Cosmetic-only randomness (particles, butterflies) uses a separate render-side RNG and must never touch game state.
- **Time:** there are two clocks (see `docs/GDD.md` §4). The **calendar** (time of day, day, season) follows the real local clock and reaches systems only as `ctx.calendar`, built in `src/core/time.ts` from an injected `now` so tests can fix the date and time zone. **Simulated time** (`clock.simMs`, integer ms) drives every timer; data durations are in seconds of simulated time. Never use floats for timers in state, and never call `Date` outside `src/core/`.
- **Modifiers:** multipliers from buffs, perks and upgrades are gathered in `computeModifiers()` and read by systems through `ctx.mods`. Add a new seam there rather than reading buffs inside a system.
- **Offline correctness:** anything timed must give the same result in one large step as in many small steps (within a stated tolerance). Every timed system has a test for this.
- **Derived values are computed, not stored** (day, season, stage, farm level, slots).

## The finished architecture (v1, after phase 09)
- `src/core/`: `game.ts` (owns state, bus, stepper; `dispatch`, `advance`, `catchUp`), `sim.ts` (`step` splits at every `msToNextSimEvent`; `processCalendar` fires season changes and the 06:00 refresh), `offline.ts` (the capped real-time walk), `time.ts` (calendar from an injected `now`), `save.ts` (`SAVE_VERSION` 13 since v2 phase 05, migrations 1→13, validation), `actions.ts`, `events.ts`, `rng.ts`, `prefs.ts` (per-device settings, not in the save).
- `src/systems/`: farming, market, shipping bin, shop, expansions, upgrades, placement, automation (farmhand + planter), auto-seller, fishing, traps, locations, cooking, buffs, modifiers, progression (XP, milestones, goals), skills, bundles, unlocks, inventory, economy, and (v2) parcels. `systems/index.ts` is the tick order.
- `src/data/`: content tables and `balance.ts`. `src/render/`: `renderer.ts`, `scene.ts` (layout and hit-testing), sprites, particles, ambient life. `src/ui/`: HUD, panels, toasts, tutorial, placement mode, `purchaseGuard.ts`. `src/audio/`: procedural sound and music. `src/main.ts` wires everything.
- `scripts/simulate.ts` + `scripts/sim/` (`driver.ts` the harness, `brain.ts` the player, `bots.ts` the strategies and schedules, `report.ts`): the balance simulator.

## v2 (from v2 phase 00; details in GDD §12, BALANCE §13, DATA_SCHEMAS §9, ART_STYLE §6)
- **World coordinates:** the world is 36 × 22 tiles and the v1 scene is its top-left corner **at the same tile coordinates** (`HOME_ORIGIN = (0, 0)` in `src/data/world.ts`). The world only grows right and down; never shift the home region. Plots keep plot coordinates and indexes, traps keep slots, trees use tree-spot indexes, decorations and buildings store the world tile of their footprint's top-left. The layout (regions, parcels, lanes, sea, town sites, tree spots) is data in `src/data/world.ts`, not constants scattered in render code.
- **The camera is per device:** its position and zoom live in prefs (`src/core/prefs.ts`), never in `GameState` or the save. Zoom is an integer pixel scale. A drag past the threshold is a pan and never runs a farm action, unless Paint mode is on (a per-device pref) or Alt is held on desktop and the press starts on a plot (v2-05).
- **Decorations are cosmetic.** Decorations, charm and town projects never feed `computeModifiers`, prices, growth or any timer, and no town project gives gold or an income multiplier. Charm is derived, never stored, and only unlocks decorations, milestones and goals.
- **Trees count real days** through `ctx.calendar.dayIndex` (monotonic, like the week index); everything else in v2 is simulated time. Animals are gentle: unfed means no product, and nothing is ever lost or reduced. Wandering animals use the render-side RNG only.
- **No games of chance**, and nothing that imitates one.

## World and camera conventions (from v2 phase 01)
- **Where things are:** the layout is `WORLD_LAYOUT` in `src/data/world.ts` (regions, lanes, sea, sand, bridge, town sites, board, tree spots, sign tiles; `regionAt(col, row)`, `REGION_NAMES`), parcels are `PARCELS` in `src/data/parcels.ts`, and `buildLayout(grid, expansions, parcels)` in `src/render/scene.ts` draws all 36 × 22 tiles. Fixed scenery that purchases change is the `SCENERY` table there (`until` / `from` an expansion, `untilParcel`); player decorations (v2-02) are not scenery.
- **Coordinates:** zones, signs and stored positions are **world tiles**; a world pixel is `tile × TILE`. Never use `HOME_W`/`HOME_H` (the v1 320 × 192) for bounds: use `WORLD_W`/`WORLD_H`, or the camera's view.
- **The camera** (`src/render/camera.ts`, pure): a centre in world px and an integer zoom in **device pixels per logical pixel**. `Renderer` owns `cam` and eases it; move it with `renderer.panToTile`, `zoomStep`, `home()`; read `viewRect`, `isTileVisible`, `tileClientCenter`, `tileRectClient`, `worldToClient` for DOM effects. It reports where it rests through `onCameraRest` and `main.ts` stores that in `prefs.camera`. A press that moves more than `DRAG_THRESHOLD_PX` is a pan (`PressGesture`), so scene clicks arrive on release: `onPlotClick`, `onZoneClick`, `onSignClick`. **Paint mode (v2-05):** with `prefs.paint` on (the Paint toggle next to the farm tools, key P) or Alt held with a mouse, a press that starts on a plot is a stroke instead: `onPaintStart` (main may decline it, e.g. while placing objects), `onPaintPlot` for each further plot, `onPaintEnd`; two fingers, the arrow keys and Home still move the view. The rules are pure in `src/render/sceneInput.ts` (`paintArmed`, `PaintStroke`, `tapActs`). **Touch taps on a tree or an animal** go through `tapActs`: the first only sets `renderer.inspected` (the label shows), the second acts; any pan (`moved()`) or a tap elsewhere clears it. The label is `src/ui/inspectLabel.ts` (hover on desktop, `inspected` on touch). **A phone's default view** centres on the plot grid (`defaultCamera(view, out, fieldCentre(grid))`), and Home goes there.
- **Rendering the world:** compose in world pixels on the world-sized frame canvas, but draw only what overlaps `viewRect` (ground chunks via `visibleChunks`, `overlaps()` for everything else) and allocate nothing per frame. Ambient life lives in the view (`Ambient.setBounds`); particles are drawn only in view.
- **The home path and the field fence** follow the field size: `pathFor(grid)` and `fenceRect(grid)` in `src/render/scene.ts` (the path runs under a small fence, then to a gate on each side, then out through the bottom rail at full size; corner sprites `obj_fence_nw/ne/sw/se`, gates `obj_fence_gate_v/h`). Every tile the path takes at any size is in `DECOR_BLOCKED`; `tests/decorRender.test.ts` and `tests/scene.test.ts` check each size.
- **Off-screen:** a toast about a place goes through `toastAt(text, tone, col, row)` in `main.ts` (adds "→ Region" and click-to-pan when it is out of view); things that want the player add a `PipTarget` in `updatePips()` (`src/render/pips.ts`, `src/ui/edgePips.ts`).
- **e2e:** address the scene through `e2e/helpers.ts` (`clickTile`, `tapTile`, `hoverTile`, `clickPlot`, `tilePoint`, `camera`), which use `window.__view` and pan a tile into view first. Never compute positions from the canvas box. Touch drags (one or two fingers) go through the DevTools protocol (`touchPath` in `e2e/touch.spec.ts`).

## Orchard conventions (from v2 phase 03)
- **Trees run on the calendar:** `src/systems/orchard.ts` reads `ctx.calendar.dayIndex` (monotonic; `calendar.maxDayIndex` in the save) and `seasonOfDay(ctx.calendar, d)`; `growOrchard` runs from `onDayStarted` and walks every day since a tree's `lastFruitDay`, so one big jump equals daily visits. A tree's age, stage and ripeness are derived, never stored.
- **Where things plug in:** actions `buySapling`, `plantTree`, `pickTree`, `moveTree`, `removeTree`; the Shop's Trees tab is `src/ui/treeShop.ts`, planting and moving is `src/ui/plantMode.ts` (it reuses the renderer's `decorateMode` click routing and `DecorGhost`, with `snap` and `markers`); trees are drawn in `Renderer.render`'s depth-merged object loop (`drawTree`, `SPOT_ORDER`), their sprites are generated in `src/render/sprites/trees.ts`.
- **Per-frame garbage (v2 phase 03 found most of it):** no `for…of` over a `Map`, no template strings, and no function that returns or takes a new double per call in the render path; creature state lives in `Float64Array`s (see `ambient.ts`), a per-plot function returns a small integer (`plotStage` uses integer maths only), and `sceneView()` rebuilds the plot sprite list only when the sim ticks or an event fires. Run `PERF_PROFILE=1` on the perf spec and read `test-results/heap.json` (an unminified build gives function names: `npx vite build --minify false`).
- **Tests:** `tests/simulate.test.ts`'s full gold-sink check is opt-in (`SPEND_REPORT=1`); the perf spec runs alone, after the other specs (a separate Playwright project), and judges the median of three measurements. Do not raise its budgets.

## Ranch conventions (from v2 phase 04)
- **Animals run on simulated time, in whole cycles:** `src/systems/ranch.ts` (`tickRanch`, first in `tickSystems`) runs `floor((cycleMs + dt) / interval)` cycles per building, each animal in turn eating a trough portion and putting a product in the store, so one big step equals many small ones. The coop is the only RNG user (the large-egg roll) and `tickRanch` runs before every other system, which keeps the draw order step-size independent. Trough refills happen at actions and at shipping-bin pickups (`ranchPickup`: the silo, then the Collecting Basket); `msToNextPickup` reports pickups while a silo or the basket exists. An empty building keeps `cycleMs` at 0.
- **Feed lives in the feed store** (`state.ranch.feedStore`, `src/systems/feedStore.ts`, v2-05), never in the bag: make, buy, the silo and troughs go through it, with `FEED_STORE_CAPACITY` per feed; feed an old save left in the bag is used after the store's. **Busy Bees** also shortens animal cycles through `ctx.mods.animalSpeedModifier` (`cycleMsOf`, whole ms); that is the ranch's only modifier seam.
- **Gentle by construction:** an unfed animal changes nothing (no event, no state), a full store waits, nothing is ever lost. A test asserts the whole state is identical after days of hunger. Do not add moods, sickness or penalties.
- **Where things plug in:** actions `buildBuilding`, `upgradeBuilding`, `moveBuilding`, `buyAnimal`, `renameAnimal`, `makeFeed`, `buyFeed`, `fillTrough`, `collectBuilding`; data in `src/data/animals.ts` (`ANIMALS`, `BUILDINGS`, `FEEDS`), products and feed items generated in `items.ts`; the Ranch panel is `src/ui/ranchPanel.ts` and building/moving is `src/ui/buildMode.ts` (it reuses the renderer's `decorateMode` routing and `DecorGhost`, like `plantMode.ts`). A building reserves its footprint **plus the tile to its right for its trough** and needs a row of grass below it for the animals (`buildingPlacementProblem`); decorations may not stand on those tiles.
- **Life in the yard is render only:** `src/render/ranchLife.ts` owns the hens and cows (typed arrays, a private generator, an insertion-sorted draw order, no allocation per frame) and is handed `view.ranch`; it never reads or writes `GameState`. Petting (`petAnimal` in `main.ts`) is hearts and a sound only. A click on a building with products collects them, otherwise it opens the Ranch panel. Sprites are in `src/render/sprites/ranch.ts`.
- **Sim equivalence tests** pin goals and perks off (`QUIET` in `tests/ranch.test.ts`): progression draws goals with the seeded RNG at the end of each step, which depends on the step size by design.
- **The bots** (`scripts/sim/brain.ts`): `tend` each look (collect, make or buy feed, fill troughs), and buy the ranch plan (`RANCH_PLAN`) as one of three turns of `spendV2` (ranch, a project's gold, decorations) after the seeds are stocked; buying it in the middle of a session starved the planter's seed and halved income. v2-05: the **starter yard** (the plan's first four steps) and the first sapling are bought straight after the land, but only with gold the planter's coming seeds will not need (`starters`, `seedGold`); other saplings are bought when leaving, after `stockSeeds`. Never let a v2 purchase run before the seeds unless it checks `seedGold`.

## Platform conventions (from v3 phase 00)
- **Where `Platform` lives:** `src/platform/` (`types.ts` the interface, `web.ts` the browser, `index.ts` picks one at boot with `detectKind` and a dynamic `import()` per adapter; shells announce themselves through `window.__HEARTHFIELD_SHELL__` or Capacitor's global). Only `src/main.ts` uses it: systems and `src/core/` never see the platform. New shells add a loader to `LOADERS` in `index.ts`.
- **Async storage, sync game:** `main.ts` awaits `SyncStore.open(platform.storage, keys)` (`src/platform/store.ts`) before creating the `Game`; after that `getItem`/`setItem` are synchronous on memory and persisted in the background, one write at a time, coalesced per key, retried with a growing delay and reported once (a toast). A key read at boot must be in that key list (`saveKeys()` + `PREFS_KEY`). Save through `SaveSlots` (`src/core/save.ts`): it rotates `save.bak` (and `.bak2`–`.bak4` on native) only after a save that validates and never over a save that failed to load. Call `saveAndFlush()` where waiting matters (pause, the autosave interval, quit).
- **Lifecycle:** `platform.onPause` → `loop.pause()`, save and flush, `engine.suspend()`; `platform.onResume` → `loop.resume()` (the offline catch-up and `onResume`, as returning to a tab always did), `engine.tryResume()` and audio again on the next gesture. The loop no longer listens to `visibilitychange` itself.
- **The back order** is `goBack` in `src/ui/back.ts`: close the top modal (or the seed picker), else leave Decorate / plant / build / placement mode (Decorate first drops a held piece), else close the panel, else return `false` for the shell. `main.ts` builds the one `BackUi`; Escape (one capture-phase listener) and `platform.onBack` both call it. Do not add Escape handlers to panels, modes or modals; give them a `back()`/`close…IfOpen()` and add it to `backUi`.
- **Safe areas:** `--safe-top/right/bottom/left` (`env(safe-area-inset-*)`, end of `src/styles.css`). The HUD and toolbar grow into the insets, so `--hud-h`/`--toolbar-h` include them; inside a zoomed element divide an inset by `--ui-scale`, outside use it as is. Check with `?debug&insets` (44 px top, 34 px bottom) or `?debug&insets=top,right,bottom,left`, or the debug overlay's "Fake notch"; `e2e/platform.spec.ts` checks a phone in both orientations.
- **Builds:** `npm run build` (Pages, `/idle-farmer/`, plus `sw.js` and `privacy.html` from `scripts/build/pwa.ts`) and `npm run build:app` (`--mode app`, `dist-app/`, `base: './'`, no debug overlay, no service worker, no `window.__game`/`__view` unless `VITE_E2E=1`; `tests/appBuild.test.ts` scans it for remote URLs). Build flags are written inline in `main.ts` (`import.meta.env.MODE !== 'app'`) so the bundler drops the dead code. Nothing may load from the network: no CDN fonts or remote assets.
- **The service worker** (`scripts/build/sw.js`, hand-written) precaches every built file cache-first and updates on the next launch; the "new version" toast reloads only when clicked. e2e blocks service workers (`serviceWorkers: 'block'` in `playwright.config.ts`) except the offline test.
- **Store kit:** `docs/STORE.md`, `docs/privacy.md`, `npm run shots:store` (sizes in `scripts/store/sizes.ts`, demo save from `npm run demo-save`), icons from `npm run icons`.

## Code conventions (from phase 01)
- **Where things plug in:** a new system is a `tickX(state, ctx, dtMs)` in `src/systems/x.ts`, called from `tickSystems` in `src/systems/index.ts`. Any timer that changes a rate mid-step (water running out, a buff expiring) must be reported by `msToNextSimEvent` so the core splits steps there. Daily and seasonal reactions go in `onDayStarted` / `onSeasonChanged`.
- **Adding an action:** add a variant to `Action` in `src/core/actions.ts`, handle it in `applyAction` by calling a system function, return an `ActionResult`. UI code calls `game.dispatch(action)` and shows `result.reason` on failure.
- **Adding a panel:** its id is in `PanelId` (`src/data/ids.ts`); replace its stub in `src/ui/panels.ts` with a `PanelDef` whose `build(body)` creates the DOM once and returns an optional `refresh()` run on every open (`wide: true` for a 480 px box instead of 360). `PanelManager` handles open/close/ESC/focus; panels never edit state.
- **Interface size** is CSS `zoom: var(--ui-scale)` on the HUD, toolbar, panels, toasts and tutorial card. Inside a zoomed element a percentage is of the parent's real size, so a zoomed panel is `width: 100%` of its host and the unzoomed host is `var(--panel-w) * var(--ui-scale)` wide. `--hud-h` and `--toolbar-h` are the bars' unzoomed heights: multiply them by `--ui-scale` in unzoomed elements, not in zoomed ones.
- **Adding a sprite:** a `SpriteDef` string grid in `src/render/sprites/*.ts`, included in `ALL_SPRITES` (`src/render/sprites/index.ts`); `tests/sprites.test.ts` checks it. Draw with `spriteFrame(id, timeMs)`, or `spriteDataUrl(id)` for DOM icons. Scene placement lives in `src/render/scene.ts`.
- **Time in the core:** only `src/main.ts` reads `Date.now()` (injected into `Game` as `now`). Tests use `zoneClock('America/New_York')` and the `at()` helper in `tests/helpers.ts`.
- **Debugging:** `?debug` (or any dev build) enables the overlay on `` ` ``; `window.__game` exposes the `Game` for e2e tests and the console.
- **e2e:** `npm run test:e2e` builds and serves the app and uses the Chromium in `PLAYWRIGHT_BROWSERS_PATH`; never run `playwright install` in cloud sessions. Look at `test-results/farm.png` after visual changes. Documentation screenshots go through `shot(name)` in `e2e/helpers.ts`: they are written to `docs/screenshots/` only with `UPDATE_SCREENSHOTS=1` (otherwise to `test-results/screenshots/`), so an ordinary run never changes the committed images.
- **Balance (phase 09):** after changing any number, run `npm run simulate` (report + CSV in `scripts/out/`) and `npx vitest run tests/simulate.test.ts`; record the change in `docs/BALANCE.md`. The bots act only through `Game.dispatch`; teach the brain (`scripts/sim/brain.ts`) about a new action rather than letting it edit state.
- **Performance (phase 09):** the render path (`Renderer.render`, `sceneView()` in `main.ts`, `plotSpritesInto`, particles, ambient) must not allocate per frame: reuse scratch objects and indexed loops. Budgets: 8 h offline on a full farm < 100 ms and 30 days < 300 ms (`tests/automation.test.ts`, `tests/qa.test.ts`, `e2e/perf.spec.ts`); a timed system that asks for data every step should cache it (see `coverageOf`, `allPlotIndexes`).

## Save rules
- Any change to the shape of `GameState` needs a `SAVE_VERSION` bump **and** a migration in `src/core/save.ts` **and** a test that migrates a fixture save of the previous version (`tests/fixtures/save-vN.json`). Add the new fixture for your version too.
- Never break an existing save. Never silently discard a save that fails to load; show an error and offer an export.
- Adding content to data tables does not need a migration unless state shape changes.

## Quality bar
- `npm run typecheck && npm run lint && npm test && npm run build && npm run build:app && npm run test:e2e` must pass before every push.
- Every new system gets unit tests. Every bug fix gets a regression test.
- TypeScript `strict`. No `any` except in migrations operating on old raw JSON.
- Keep runtime dependencies at zero unless a phase prompt allows one.

## Scope rule
- Stay inside the current phase's prompt. If you have an idea outside it, add a line to `docs/IDEAS.md` (what, why, which phase could own it) instead of building it.
- Small typed seams for later phases are fine; behaviour is not.

## Handoff rule
Before finishing, add a section to `docs/PROGRESS.md` for your phase with four headings: **Built**, **Deviations** (from the prompt or docs, with reasons), **Known issues**, **Next-phase notes** (exact files, action names and patterns the next session should use). If you changed numbers, update `docs/BALANCE.md` and add tuning notes.

## Git
- Small, descriptive commits. One PR per phase against `main`, titled as the phase prompt says.
- Do not commit build output, `node_modules`, `test-results/` or `scripts/out/`.
